# 多团队第一批：本地测试说明

开发分支：`codex/multi-team-foundation`。本批为账号与地点基础功能，不是完整植保工单上线。

## 本地运行

在项目根目录执行：

```powershell
.venv/Scripts/python.exe internal_server/scripts/run_multi_team_preview.py
```

打开 <http://127.0.0.1:8786/ops/>。脚本只监听本机回环地址，使用
`.tmp-pm-review/multi-team-preview/db.sqlite3`，不会打开真实业务数据库。
测试媒体、AI 目录独立，邮件使用内存后端；不会启动生产同步、派工或邮件定时任务。
重启保留已填写的地点、成员身份及共享变更；不自动重新启用已停用的成员。

所有以下账号的初始测试密码为 `Pilot-Test!2026`，仅适用于此独立示例库：

| 账号 | 可测试的身份 |
| --- | --- |
| `pilot-admin` | 平台管理员；可管理两个团队成员、创建本地测试账号 |
| `irrigation-manager` | 灌溉经理；可进入原灌溉页面、引入并共享区域 |
| `pest-manager` | 植保经理；可管理植保地点与普通成员，不能访问灌溉业务接口 |
| `pest-field` | 植保一线；可查看授权地点与目录，不能管理成员、地点或共享关系 |
| `dual-role` | 灌溉一线 + 植保经理；通过顶部选择身份后点击“切换” |

原来的本地数据库和已有测试服务器不需要迁移。停止本服务器使用运行终端的 Ctrl+C。
当前脚本不自动重载代码，后续更新后需要重启服务器；重新读取页面以加载更新。

## 建议测试顺序

1. 使用 `dual-role` 登录，切换植保经理与灌溉一线。植保身份显示“团队成员”和地点新增入口；灌溉一线身份不显示这些管理入口。
2. 以植保身份进入“地点与共享区域”：能看到共享绿地、行政楼、房间和监测点，看不到“灌溉专用区”。
3. 新增建筑或房间，使用任意编号（如 `LOBBY-A`）或留空。地图定位和上级地点也可选；没有边界仍可保存。
4. 使用 `irrigation-manager` 查看共享绿地详情，取消对植保的共享。植保刷新后该地点从列表/地图消失，原详情地址也不可访问。重新共享后恢复。
5. 在“引入灌溉区域”中按名称/编号选择现有区域；建立的是引用，原区域的边界、来源和业务资料不被修改。接收团队不能编辑或再次共享它。
6. 使用 `pest-manager` 访问 `/irrigation/`、`/api/zones-payload/`、`/user-management/` 等原灌溉入口，应被拒绝。只获得植保经理身份不会创建全局 `ManagerProfile` 或赋予 Django staff 权限。
7. 使用 `pilot-admin` 为一个账号增加另一团队身份；普通团队经理只能管理本团队普通成员，不能授予经理角色或更改其他团队身份。
8. 植保目录保留 7 大类、208 个普通节点和 7 个附属步骤，共 215 个条目；可以展开不同深度的分支，重复名称按原路径保留。目录为只读参考草案，不创建工单或调度任务。

## 当前实现边界

- 一账号多团队、团队内角色、停用身份、平台与团队管理分离、切换身份审计。
- 中立地点 UUID；编号可选且只在所属团队内唯一。支持建筑、楼层、房间、监测点等类型、可选上级和定位点。
- 地点由团队拥有，可向指定团队授予只读共享；共享信息不包含灌溉备注、工单统计、人员资料或照片。
- 关联灌溉区域时实时读取原区域的当前生效边界，不复制手绘/DXF 坐标，不改变其来源。原区域的几何仍从原灌溉入口管理。
- 植保参考目录导入幂等，保留来源版本、行号、父子层级和附属步骤；本批不发布可执行流程。
- 新功能默认关闭（`MULTI_TEAM_ENABLED=False`）；普通生产配置行为保持原状。本地预览脚本单独启用。

兼容期的原灌溉应用仍是一个业务范围，只有明确标记的旧灌溉团队、匹配的旧账号角色可以进入。
这不是所有旧页面已经完成按任意细分团队过滤；也不能把多个灌溉子团队分别授予旧系统经理权限后，声称已经实现子团队隔离。
新植保账号无法进入旧入口，避免复用全局经理判断时泄露数据。平台管理员的跨业务权限是明确的。

## 普通环境的启用准备（此批不在生产执行）

1. 备份并在副本执行 Django migrations。
2. 执行 `bootstrap_operations` 建立两个业务和团队。
3. 需要迁移原有账号时，在审核过的账号副本上使用 `bootstrap_operations --assign-legacy`：仅把尚无成员关系的旧有效账号映射到灌溉团队，不提升全局权限，不重新启用已停用身份，不把新植保账号追加成灌溉经理。
4. 手动确认平台管理员名单和成员身份，再启用 `MULTI_TEAM_ENABLED=True`。原来仅有 `is_staff` 的账号不会因此成为多团队平台管理员。
5. 使用 `import_pest_reference PM管理_层级结构整理版.md` 导入只读参考；选定区域再逐一共享。

下一批：植保案件与巡查执行记录、业务归属的工单读写路径、通用计划目标和独立轮转池。
在独立派工池和权限作用域完成前，不向现有灌溉调度表直接加入植保计划。
