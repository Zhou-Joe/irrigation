# PM 调度与后台管理审查

业务规则保持为：提前 `lead_days` 天生成工单；从计划执行日期开始有一个完整维护周期，超过截止日期才逾期，截止日当天仍可正常完成。

| 问题 | 影响与修复 |
|---|---|
| 编辑弹窗未提交区域，后端直接清空关联 | 保留未提交的区域；弹窗及独立表单增加区域多选，主动清空需明确提交 |
| 新建/编辑缺少编号、外键和资产校验 | 使用同一组 ModelForm 校验，重复编号和无效关联返回 400；保存和区域关联在同一事务中 |
| 月末计划使用 rrule 漏掉短月份 | 使用原基准日计算日历周期，1/31 → 2/28 → 3/31；页面下一期和周期窗口共用算法 |
| 修改计划频率改变旧工单逾期时间 | 派发时保存截止日期；新增迁移回填历史工单，旧期限独立于后续编辑 |
| 班组匹配只看首个区域或任意首个工人 | 匹配完整资产范围并保存负责班组；无匹配或多班组时记录原因，交由经理指定 |
| 自动略过只有混合单位的数量，没有明细 | 每次实际运行保存结果；后台展示生成张数、按计划计的其他数量，以及每个 PM 的原因 |
| 计划保存、派发、延期可能交错更新 | 同一计划内派发使用事务和计划锁；各期工单继续按 plan + scheduled_date 唯一去重 |
| 任意登录用户可以读取或延期其他班组任务 | 详情、延期、完成和完成记录编辑共用可见工单范围，已处理或未来任务不能新建完成记录 |
| 重复完成可能插入孤立记录或报唯一约束错误 | 创建完成记录前锁定并检查派发状态，重复提交返回冲突；完成时关闭待审批延期 |
| 延期后保留旧基准的提前生成任务 | 同一事务内跳过旧基准下后续未完成任务，关闭相关延期，保留已完成历史 |
| 完成统计用单个主导计划的周期套全部计划 | 每个计划按自己的频率和基准日统计；尚未存在的上期不会落入“全部历史” |
| 补发旧日期产生新 ID，分页按 ID 会漏单 | 使用计划日期与 ID 组成的排序边界分页，和列表排序一致 |
| 重置安排删除周期内/未来工单并隐式重排 | 改为清理真正逾期的工单，保留原计划基准、当前周期、未来和历史记录 |
| 首次管理页访问没有 CSRF cookie | 页面初始化 cookie；真实浏览器保存成功，新增开启 CSRF 校验的回归测试 |
| 原始 JSON 可提前关闭 script 标签 | 使用 Django json_script 安全输出；区域名带 script 标签的回归测试通过 |
| 页面为计数预取全部工单、操作后筛选丢失 | 工单数改为数据库聚合，资产关联预取；刷新保留 URL 查询参数，保存后刷新分类和下次到期 |

验证：52 项 PM 回归测试；独立测试库中完成浏览器编辑保存，确认提前生成天数 0 与两个区域均保留；展开派发记录确认未关联区域的原因可见，浏览器无 JavaScript 错误。测试数据、服务与业务数据库独立。

相关现有测试共 75 项通过。全库使用独立内存缓存执行共 137 项测试，136 项通过，1 项因缺少既有 `Test dxf.dxf` 文件跳过；默认共享文件缓存环境的全库运行曾长时间不返回，因此验证没有复用业务缓存。模型与迁移一致性检查通过。

本地数据库已先用 SQLite 在线备份，再成功应用 0131 迁移；页面验证结束后已关闭测试服务并删除合成数据数据库。默认 Windows 开发设置仍有两个既有文件缓存路径警告，与本轮 PM 修改无关。

数据库升级：`core.0131_pm_deadlines_and_dispatch_runs` 新增工单截止日期与派发结果表。上线需运行正常数据库迁移。
